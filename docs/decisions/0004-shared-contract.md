# 0004: Client/server contract

## Status
Accepted (M0-8)

## Context
ADR 0003 picked graphql-kotlin, so the server's schema is generated from Kotlin classes and the SDL comes out of that process. The client uses Apollo Kotlin in `shared`. Two ways to share the contract were compared on 2026-10-19:

| | A: GraphQL schema as contract | B: Shared Kotlin DTOs |
|---|---|---|
| Source of truth | Server Kotlin types, exported to a committed SDL file | `@Serializable` DTOs in `shared/commonMain` |
| Client models | Generated by Apollo from the SDL and `.graphql` operations | Hand-shared DTOs. Apollo still generates its own models, so the DTOs either sit unused next to them or Apollo is replaced by Ktor client and hand-written query strings |
| Module coupling | None. The server does not depend on `shared` | The server depends on `shared`, which needs a `jvm()` target, and the mobile data layer and sync code end up on the server classpath |
| Change review | Every API change shows up as a diff of `schema.graphqls` | API changes are mixed into Kotlin diffs |
| Offline/CI build | The client builds from the committed SDL without a running server | The client builds without a running server |
| Cost | Two model sets (server types and Apollo types) | One model set, but server and client release together |

Prototype (thrown away after the test, as in M0-7) on Kotlin 2.4.20, AGP 9.4.0, Ktor 3.6.0:
- `server`: graphql-kotlin 11.0.0, a `hello` query, and a test that calls `toSchema(...)` and `GraphQLSchema.print()` and writes `shared/src/commonMain/graphql/schema.graphqls`. **Passed.**
- `shared`: Apollo Kotlin 5.2.0 (`com.apollographql.apollo`, latest release, 2026-09-16) with a `HelloQuery.graphql`. `:shared:generateApolloSources` generated `HelloQuery` and its adapters. `:shared:compileAndroidMain` and `:shared:testAndroidHostTest` **passed** under the `com.android.kotlin.multiplatform.library` plugin, with no Kotlin version warnings.

## Decision
Use **A: the GraphQL schema is the contract.**

- The server owns the schema as graphql-kotlin Kotlin types in `server`. `shared` never appears in the server's dependencies.
- The SDL is committed at `shared/src/commonMain/graphql/schema.graphqls`, which is Apollo's default source directory.
- The SDL is exported by a server test, not by the `graphqlGenerateSDL` Gradle task:
  - The test builds the schema with the same `toSchema` config and hooks the runtime uses.
  - By default it compares the printed SDL to the committed file and fails on drift.
  - With `-PupdateSchema` it rewrites the file instead.
  - Reasons: the Gradle task uses reflection with default hooks, so custom scalar hooks would differ from the runtime; it is not part of the build lifecycle; and it adds another plugin version to track.
- Client operations (`.graphql`) live next to the SDL in `shared` and are the only thing the client adds to the contract.

## Consequences
- **Routing order for any API change:**
  1. Server schema and resolvers.
  2. SDL export, committed.
  3. Client operations and data layer in `shared`.
  4. Views.

  The client cannot compile an operation until the SDL contains its fields, which is why the order is server first.
- M1-2 implements the export test and drift check. M1-1 configures Apollo against the committed file. The ticket text already matches.
- CI catches drift through `:server:test`. A server change that alters the schema without regenerating the SDL fails the build.
- The printed SDL includes graphql-java's built-in directives (for example `@experimental_disableErrorPropagation`). Apollo 5.2.0 accepted them in the prototype.
- Not verified, deferred to M1-5:
  - Custom scalars (`Instant`, IDs), which need matching graphql-kotlin hooks and Apollo scalar adapters.
  - Subscriptions.
  - Apollo with iOS targets enabled.
- Apollo 5.x builds with KGP 2.3.10. Kotlin 2.4.20 was exercised only by the prototype.
